# Perfis de acesso · registro da implantação (06–07/10/2026)

Este documento registra o que foi feito ao implantar o módulo `perfis-acesso` no ambiente da app 100 (workspace `WKSP_CORLIXHUB`), os problemas encontrados no caminho e como cada um foi resolvido. O passo a passo genérico continua em [`Etapas-perfis-acesso.md`](./Etapas-perfis-acesso.md). Aqui fica o histórico **deste ambiente**.

## Resumo

- Os papéis Colaborador, Gestor e Admin RH e a autorização `ADMIN_RH` foram criados no Builder e exportados para `corlixhub/`.
- `CARGO_PAPEL` e `PKG_PERFIS_ACESSO` foram instalados. O seed (`02`) criou cargos com nomes que **não batiam** com os cargos já usados pelos colaboradores. Por isso os papéis foram vinculados **à mão** aos cargos antigos (§3).
- Página 14: a LOV de Gestor passou a usar `CARGO_PAPEL`, o login ficou obrigatório e foi criado o processo "Atribuir papéis do cargo".
- A numeração automática de `COLABORADOR` foi corrigida. O cadastro pela P14 dava `ORA-00001`.
- As contas da equipe do Corlix Hub receberam o papel Colaborador pelo Builder. As contas de teste foram recriadas pela P14.

## 2. Problemas encontrados e soluções

| # | Sintoma | Causa | Solução |
|---|---|---|---|
| 1 | Na tela de criação só havia "pre-configured scheme from the gallery" e "copy of an existing authentication scheme" | Assistente errado: **Authentication** Schemes (login) em vez de **Authorization** Schemes | Cancelar e usar Shared Components > Security > Authorization Schemes |
| 2 | Cargos antigos com colaboradores ficaram sem papel | O `02` só reaproveita cargo com nome idêntico. Os nomes do banco são diferentes (ex.: "Diretor Geral (CEO)" × "Presidente (CEO)") | Vínculos manuais nos cargos antigos (§3.1) |
| 3 | `ORA-03405: End of query reached` | SQL Commands executa um comando por vez e não aceita `;` + `commit;` | Rodar só o comando, sem `;`. O Autocommit já grava |
| 4 | `ORA-12704: character set mismatch` | `unistr()` devolve NVARCHAR2, e foi misturado com VARCHAR2 num `union all` | `to_char(unistr('publicador-de-conte\00FAdo'))` |
| 5 | `ORA-01403: no data found` em `WWV_FLOW_ACL_API` | `apex_acl.add_user_role` precisa de sessão da app 100. O SQL Commands não tem | Atribuir pelo Builder (§6.1) ou por SQLcl/SQL Developer |
| 6 | `ORA-20987: Access to session state is disabled` em `apex_session.create_session` | O SQL Commands roda na sessão do Builder e bloqueia criar sessão de aplicação | Mesmo caminho do item 5. A §6.2 do guia foi reescrita |
| 7 | `ORA-21002: attempted to reraise a cleared error` | O `delete_session` no `exception` limpava o erro antes do `raise` | Guardar `sqlerrm` + backtrace numa variável antes de encerrar a sessão |
| 8 | LOV de Cargo mostrava nomes de colaboradores | Query da §4.1 colada em `P14_CARGO` em vez de `P14_GESTOR` | Query original de `P14_CARGO` restaurada |
| 9 | `ORA-00001 … COLABORADOR (ID_COLABORADOR)` ao salvar na P14 | Identity de `ID_COLABORADOR` em `START WITH 1`, mas os 291 colaboradores foram carregados com IDs manuais | `alter table colaborador modify id_colaborador generated by default as identity (start with limit value)`. Incluído no `02` |
| 10 | Home: `Uncaught SyntaxError: Invalid or unexpected token` | `onerror` do card "Meu gestor" com a string `'#APP_FILES#de` / `fault-user.jpeg'` quebrada em duas linhas | Linha unida em `p00001-home.apx` (ver pendências) |

Alguns são cargos novos de verdade (ex.: 620 Gerente de Marketing, 623 Analista de Comunicação Interna, 630 Tech Lead). Os outros são **duplicatas** dos cargos antigos e aparecem na LOV de Cargo da P14. **Se o `02` rodar de novo, ele não os duplica outra vez** (busca pelo nome), mas também não os remove.

Para listar o estado atual:

```sql
select d.id_departamento, c.id_cargo, c.nome,
       count(distinct col.id_colaborador) as colaboradores,
       listagg(distinct p.cd_papel, ', ') within group (order by p.cd_papel) as papeis
  from cargo c
  join departamento d on d.id_departamento = c.id_departamento
  left join colaborador col on col.id_cargo = c.id_cargo
  left join cargo_papel p on p.id_cargo = c.id_cargo
 where c.id_empresa = 1
 group by d.id_departamento, c.id_cargo, c.nome
 order by d.id_departamento, c.nome
```

(No SQL Commands, mude **Rows** para 1000: o padrão é 10.)

### 3.3 Numeração automática

`DEPARTAMENTO`, `CARGO` e `COLABORADOR` agora continuam a partir do maior ID (`start with limit value`). As outras tabelas carregadas com IDs manuais podem ter o mesmo problema. Se aparecer `ORA-00001` na PK ao inserir, aplique o mesmo `alter table`.

**Ponto de atenção sobre a ordem de execução da P14.** No `f100.sql`, "Salvar Dados Colaborador" (10) e "Criar usuário APEX" (20) estão no ponto `ON_SUBMIT_BEFORE_COMPUTATION` (*After Submit*). Já "Atribuir papéis do cargo" (30) está em `AFTER_SUBMIT` (*Processing*). A ordem entre eles está certa, porque os papéis são atribuídos depois de a conta existir. Mas o insert do colaborador e a criação da conta acontecem **antes das validações**, inclusive a "Validar Confirmação de Senha". Isso já era assim antes do módulo. Vale testar uma senha divergente e, se ficar colaborador ou conta criados, mover os processos 10 e 20 para **Processing**.
